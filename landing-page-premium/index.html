Design Principles

Architecture-first approach to local secret orchestration.

Zero Persistence

Secrets are never written to host storage. They reside strictly in process memory and are streamed directly into target container memory-mapped filesystems (tmpfs).

Event-Driven

Leverages the Docker Event stream for real-time lifecycle hooks. Responds instantly to container start, stop, and update events without continuous CPU-heavy polling.

Docker-Native

Operates as a first-class Docker plugin. Integrates with existing Docker Compose workflows via standard labels, requiring zero changes to application code.

System Architecture

A modular approach to secret distribution.

Watcher Engine

Monitors the Docker API for lifecycle events and specific labels (`dso.reloader=true`). Identifies target containers for reconciliation.

Reloader Controller

Orchestrates atomic updates. Verifies container health post-injection and triggers automated rollbacks on failure.

Tar Streamer

Low-level injection mechanism. Streams secret data directly into the container's virtual filesystem using `tar` over the Docker socket.

Operational Excellence

Resilient secret orchestration for production environments.

Atomic Secret Rotation

DSO ensures that secret updates are atomic. During rotation, the system verifies the integrity of the new secret stream before committing changes to the container lifecycle.

Automated Rollbacks

If a container fails its health check precisely after a secret update, DSO can automatically revert to the previous known-good version of the secret to maintain availability.

Rollout Strategies

Strategy: RESTART Standard
Strategy: RELOAD (SIGHUP) Hot-Reload
Strategy: MOUNT Native File

Strategies are defined per-secret in `dso.yaml`, allowing granular control over application behavior.

Security Engineering

Hardened by design. Secrets belong in memory, not on disk.

Authenticated Socket Only

Communication with the Docker Engine is strictly restricted to the local Unix socket, leveraging host-level ACLs.

Zero-Persistence RAMfs

Secrets are mapped to `tmpfs` mounts. They are lost immediately if the host or container loses power, preventing cold-boot or forensic theft.

Least Privilege Agent

The DSO agent requires only set capabilities (`CAP_CHOWN`, `CAP_FOWNER`) to manage secret mounts, avoiding full `root` escalation where possible.

Threat Mitigation
  • Unauthorized Image Access Blocked
  • Cold-Boot Disk Theft Mitigated
  • Secret Leakage in Logs Redacted

Example usage

Two files. That's all you need.

/etc/dso/dso.yaml 
# Provider configuration
provider: aws

config:
  region: us-east-1

agent:
  watch:
    polling_interval: 2m

secrets:
  - name: my-app-secret
    inject: env
    mappings:
      DB_PASSWORD: DATABASE_PASS
      DB_USER:     DATABASE_USER
docker-compose.yaml 
services:
  app:
    image: my-app:latest
    environment:
      - DB_PASSWORD_FILE=/run/secrets/DB_PASSWORD
      - DB_USER_FILE=/run/secrets/DB_USER

  db:
    imagepostgres:16
    environment:
      - POSTGRES_PASSWORD_FILE=/run/secrets/DB_PASSWORD
$ docker dso compose up -d # DSO reads dso.yaml → fetches from AWS → injects into containers → starts stack

Security Model

Built for trust, not just compliance

Every design decision in DSO is a security decision. Here's exactly what happens with your secrets.

Memory-Only Store

Secrets are held in the agent's in-process RAM. Never written to the filesystem. Purged on shutdown.

Unix Socket Transport

CLI↔Agent communication happens over a local Unix socket. No network exposure, no TLS to manage.

IAM Role Auth — Zero Credentials on Host

DSO uses EC2 Instance Profiles, Managed Identity, and Vault AppRole. No static keys stored on the machine.

Structured Audit Logs

Every fetch, rotation, and strategy decision is logged in JSON. Forward to Splunk, Datadog, or CloudWatch.
